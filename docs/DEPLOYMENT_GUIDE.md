# SOCRATES Production Deployment Guide

> **Branch Reference:** [`feature/labour-intelligence`](https://github.com/AnuragShivoham/P-S/tree/feature/labour-intelligence)

This guide documents the recommended split-deployment architecture for SOCRATES, why it is necessary, and step-by-step instructions for deploying the frontend on **Vercel** and the backend on a **Persistent Node/Container Service** (Railway, Render, Fly.io, or VPS).

---

## 1. Architectural Model

```text
┌─────────────────────────────────┐
│         Vercel (Edge)           │
│   React 18 + Vite (SPA)         │
│   https://socrates.vercel.app   │
└────────────────┬────────────────┘
                 │
                 │ HTTPS (REST API)
                 │ WSS (WebSockets: /session, /terminal)
                 ▼
┌────────────────────────────────────────────────────────┐
│   Persistent Node Host (Railway / Render / Fly.io)     │
│   Express + WebSocketServer + node-pty + SQLite (WAL)  │
│   https://api-socrates.example.com                     │
│                                                        │
   │   • Persistent Volume: /app/data/socrates.db           │
   │   • Project Sandboxes: /app/workspace/{projectId}      │
│   • PTY Shell Execution: bash / sh / powershell        │
└────────────────────────────────────────────────────────┘
```

### Why Not Deploy the Backend to Vercel Serverless?
The SOCRATES backend requires stateful infrastructure that serverless functions cannot provide:
1. **Interactive Terminal (node-pty):** Spawns long-lived PTY pseudo-terminals running real bash/sh shells with bi-directional streaming over WebSockets.
2. **Local Workspace Filesystem:** Students create, edit, compile, and execute files inside `./workspace/{projectId}`.
3. **Database (`node:sqlite`):** Uses Node 22's native SQLite with Write-Ahead Logging (`WAL`). Serverless containers are ephemeral and will destroy the database upon spin-down.

## 2. Frontend Deployment on Vercel

### Step 1: Import Repository
1. Navigate to [vercel.com/new](https://vercel.com/new) and import the repository: `AnuragShivoham/P-S`.
2. Select the branch: `feature/labour-intelligence` (or `main` once merged).

### Step 2: Configure Project Settings
In the Vercel project configuration screen:
- **Framework Preset:** `Vite`
- **Root Directory:** Click "Edit" and choose `frontend` *(Essential: do NOT leave as root)*
- **Build Command:** `npm run build` (default)
- **Output Directory:** `dist` (default)
- **Install Command:** `npm install` (default)

### Step 3: Add Frontend Environment Variables
In Vercel **Settings → Environment Variables**:

| Variable | Required? | Example Value | Description |
|---|---|---|---|
| `VITE_API_URL` | **Yes** | `https://api-socrates.example.com` | Backend HTTPS origin only (no `/api/v1` suffix or trailing slash). Production API requests fail clearly if this is missing. |
| `VITE_WS_URL` | Optional | `wss://api-socrates.example.com` | Override for WebSocket URL. If omitted, automatically derived from `VITE_API_URL` (`https://` → `wss://`). |
| `VITE_GOOGLE_CLIENT_ID` | Optional | `368735634595-xxx.apps.googleusercontent.com` | Google OAuth Client ID for sign-in button. Must match the backend. |

> [!TIP]
> Use `frontend` as the Vercel Root Directory. Its Vercel config provides the SPA fallback for routes such as `/dashboard`, `/ide`, and `/labour-intelligence`. API calls go directly to `VITE_API_URL`; the SPA fallback is not an API proxy.

## 3. Backend Deployment (Persistent Container Host)

Deploy `backend/` to a persistent/container host that supports **Node.js 22.5+** and **Persistent Disks** (`node:sqlite` is used by the active database):
- **Railway:** Recommended (One-click Dockerfile or Nixpacks + Persistent Volume)
- **Render:** Web Service + Persistent Disk
- **Fly.io:** Fly Launch + Fly Volumes
- **DigitalOcean App Platform / VPS / Docker**

### Render Blueprint (prepared)

The repository root includes `render.yaml` for the existing Docker backend. In Render, create a **Blueprint Instance** from the `feature/labour-intelligence` branch and select the repository. The Blueprint uses `backend/Dockerfile`, the `/health` health check, and a persistent disk mounted at `/app/data` for SQLite, uploaded media, and workspaces. Render requires a paid web-service plan for persistent disks; confirm its current price before creating the service. The backend stays a single service; Labour Intelligence is not deployed separately.

Render will prompt for `GROQ_API_KEY`, `GOOGLE_CLIENT_ID`, `ADMIN_EMAILS`, `ADMIN_PASSWORD`, `EMAIL_USER`, and `EMAIL_PASS`; provide them in Render, not Git. Set `ADMIN_EMAILS` to your trusted bootstrap-admin email(s), and configure a working SMTP account or users cannot receive OTPs. The JWT signing secret is generated by Render. If Google sign-in is not enabled, remove its environment entry from the service in Render. After the service is live, set Vercel's `VITE_API_URL` and `VITE_WS_URL` to its HTTPS and WSS origins, and update `FRONTEND_URL` here if the production frontend URL changes.

> **Security hold before making the service public:** The current backend still has unauthenticated or optional-auth endpoints for project previews, media, and several Labour Intelligence operations. The PTY WebSocket starts a shell in the container, and its command filter is not a security sandbox. Review and harden these access controls before using this public service with real users or data. A Vercel frontend origin/CORS allowlist does not protect API endpoints from direct callers.

## 4. Google OAuth Configuration

When running with a separate frontend and backend domain:
1. Open [Google Cloud Console > APIs & Services > Credentials](https://console.cloud.google.com/apis/credentials).
2. Edit your **OAuth 2.0 Client ID**.
3. Under **Authorized JavaScript origins**, add:
   - `http://localhost:5173` (for local development)
   - `https://your-app.vercel.app` (your Vercel production frontend)
   - Each specific preview origin you intend to use (Google OAuth origins do not support a wildcard)
4. Under **Authorized redirect URIs**, ensure your frontend callback URL is listed if using redirect flow.

## 5. Deployment Configuration Notes

1. **Frontend API Client (`frontend/src/api/client.js`):**
   - All REST requests use the centralized API URL helper. In local development without `VITE_API_URL`, requests use `/api/v1` and the Vite proxy; production builds require `VITE_API_URL` to prevent requests from silently going to the Vercel SPA host.

2. **Unified URL & WebSocket Helper (`frontend/src/api/config.js`):**
   - Added `getWsUrl()` that automatically resolves WebSocket protocol (`ws:` / `wss:`) and routes to `VITE_WS_URL`, `VITE_API_URL`, or local dev port `3001`.
   - Updated `IdePage.jsx`, `Terminal.jsx`, `useSocket.jsx`, `WebPreview.jsx`, and `ProblemDetailPage.jsx` to use centralized URL generators instead of hardcoding `localhost:3000` or `:3001`.

3. **Backend CORS (`backend/src/server.js` & `backend/src/config.js`):**
   - Reads `FRONTEND_URL` and `ALLOWED_ORIGINS` as exact origins.
   - Broad `*.vercel.app` preview access is strictly opt-in through `ALLOW_VERCEL_PREVIEWS=true` and is not enabled merely because the production origin is on Vercel.

4. **MCP Service Safe Require (`backend/src/services/mcpService.js`):**
   - Wrapped `@modelcontextprotocol/sdk` imports in safe try/catch guards to prevent initialization crashes when optional SDK packages are absent.

5. **Persistent workspace path:**
   - File operations and terminal sessions share `WORKSPACE_PATH`. The Render Blueprint sets it to `/app/data/workspace` on the attached persistent disk; the Docker Compose development mount uses `/app/workspace`.

6. **Container runtime:**
   - The Render Docker entrypoint fixes persistent-volume ownership, then starts Node as the unprivileged `node` account. The PTY terminal is forcibly disabled whenever `NODE_ENV=production`.

7. **SPA Rewrites (`frontend/vercel.json` & `vercel.json`):**
   - Both frontend-root and repository-root Vercel deployments retain the SPA fallback. The recommended setup is still Root Directory `frontend`.
